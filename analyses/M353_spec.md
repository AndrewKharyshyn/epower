## 1. Facts (script-checked)
- The registry entry `i_offset` says "BMS current offset (per drive)", value "fitted per drive (two-pass solve)", class `derived_per_drive`. On disk `I_offset_A_applied` is ONE corpus constant (475 drives, 1 value at 4 dp: -0.3858 A) and `I_offset_2p_A_applied` likewise (-0.3869 A, 475 drives). The offset is stamped only where the SoC-anchored energy residual exists (M349 root cause).
- Its `usedBy` is ["gross/net energy", "GTC"]; compute_drive_summary_v6 (`_v5_postprocess_master`, ev-battery comment ~1496) states the offset is a net-draw correction deliberately NOT applied to gross quantities (gross throughput, GTC). The payload already carries the deterministic sensitivity `energyUncertaintyMC.offsetGrossSensitivity` (offset applied before the discharge/charge split raises gross throughput by throughputShiftPct = 0.3406 %, shift 5.1005 kWh), so the "+0.34 % variant" is bound to that key, not typed.
- model_constants.py has no per-constant class; the registry assigns classes by hand. `FUEL_VOL_ERR` comment says "ECU fuel volume" (the logger is Car Scanner ELM OBD2: logged/app-calculated).

## Rev 2 (Director: "revise"; all changes accepted; Rev 1 had the offset backwards)
1. The published offset is the two-pass solve: `offsetUncertainty.pointEstimateA` = `I_offset_2p_A_applied` = -0.3869 A (correctionScope.appliesTo = `*_corr2p`). -0.3858 is the v5 single pass feeding the retired `net_draw_*_corr` columns; shown only as "v5 single-pass". (Note for the record: `fuel_recon.py` and the M349 repair use `I_offset_A_applied`, the v5 single-pass value, by the pre-existing convention; the two constants differ by 0.0011 A; not changed here.)
2. `usedBy` = `correctionScope.appliesTo` (net_draw_kwh_corr2p, energy_residual_kwh_corr2p, net_draw_per100km_corr2p), read from the payload; the sensitivity names `notAppliedTo` (gross discharge/charge/throughput, GTC, FCE).
3. Three populations stated separately: fitted on the domain-clean drives (n = offsetUncertainty.nDrives, 473, excludes f_domain_2p, nDays), stamped on the 475 drives with a SoC-anchored residual, subtracted from every drive with V_pack_median and duration. 475 is never called the fit n.
4. "Corrected energy residual" = SoC-anchored residual minus the offset energy; it sums to ~0 on the fit set by construction and depends on CAP_KWH (capacitySensitivity): not an independent validation.
5. "Constant" = one corpus-wide constant re-solved per corpus build (it moves on ingestion); ci95A from `offsetUncertainty` is shown.
6. `CONSTANT_CLASS` is the single source of the class for the registry entries built from model constants: the builder keeps an id -> [MC symbols] map (fuel_density, fuel_lhv, bsfc_surface [BSFC, BSFC_FLOOR], eta_gen_pe [ETA_GEN, ETA_PE], p_aux, cold_gate_engine [COLD_OIL_T_C, COLD_T_C]) and takes `klass` from `CONSTANT_CLASS` (all components must agree, else it raises). The registry's hand-typed klass literals for those entries are removed. Test: every `CONSTANT_CLASS` value is in KLASSES, the covered-entry count is >= 6, registry klass equals the mapped class. FUEL_VOL_ERR, I_OFFSET_SIGMA_A and COLD_MULT carry classes in `CONSTANT_CLASS` but are not registry entries.
7. New class `derived_corpus_constant` replaces `derived_per_drive` in KLASSES, the builder docstring and the jsx `ASSUMPTION_KLASS` map (label "Derived, corpus constant"; the old map entry is dropped); a required A2 check asserts the rendered label.
Gate rules: forbidden phrases "fitted per drive", "BMS current offset per drive", "Derived per drive", "Sign-checked per drive", "measured offset" (phrase rules; scoped by their specificity to the offset row); required in the payload row and the rendered row: "one corpus-wide constant", "two-pass", "not applied to gross throughput, GTC or FCE", "Derived, corpus constant". Wording: estimated, not measured.
