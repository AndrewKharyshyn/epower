## 0. Why
Owner (2026-11-21): the cloud export is auxiliary; exports arrive "ideally with each ingestion, but NOT guaranteed"; the importer must be an optional, non-blocking, idempotent stage; coverage is reported per drive as "no cloud data yet", never as a gap in the OBD study. Since then six cloud tools exist and are run by hand (M729 coverage, M730 clock offset, M733 tyre, M734 thermal, M737 grade G0, M739 unlogged exposure; plus the importer M729). `docs/open_items.md` tells the operator to rerun M737 and M739 "at each ingestion". Hand reruns are the failure mode this repo's rules warn about (an ingestion is not complete until every refresh that is owed has run). The stage list has no optional stage (`tools/ingest_stages.json`: "A stage failing stops the run").

## 1. Constraints
- The stage MUST NOT be able to stop or fail an ingestion: once the wrapper has started, its exit code is 0; every tool failure is recorded, not raised. A missing store, a missing export, an unreadable ZIP, a tool timeout give a recorded `skipped` / `failed` row and exit 0.
- Read-only on `drive_master.csv`, `raw/`, `summary_*.json`, payload keys, dashboard, frozen winter files (M726). The stage writes only the `analyses/M7xx_*` outputs these tools already write plus one new status file `analyses/cloud_stage_status.json`. The wrapper asserts the `drive_master.csv` MD5 before and after each tool; a change aborts the remaining cloud tools and is recorded (should be impossible).
- It runs after the master and arrays are final for the ingestion (the drive windows are the new ones) and before `release_check`; `release_check` does NOT read its outputs and does not fail on them (optional by construction). Placed immediately before `release_identity` unless the Director review finds a reason otherwise.
- Public repository: the tools already write aggregates (and per-drive-day tables already committed); the stage adds no new output class.
- Environment: store from `XT_CLOUD_STORE` (else the tool default); export folder from `XT_CLOUD_EXPORTS` if set (importer `--auto`), else import is skipped. No path is guessed.
- Idempotent and deterministic: a rerun with unchanged inputs gives byte-identical outputs (all tools seed 42, 4000 draws). The status file records input fingerprints (store manifest sha256, master MD5, raw manifest sha256); a tool whose fingerprint is unchanged is `skipped_up_to_date` unless `--force`.

## 2. Design
`tools/cloud_stage.py`: ordered list of (id, command, timeout, outputs): import (only when `XT_CLOUD_EXPORTS` is set and holds ZIPs), coverage, clock_offset, tyre, thermal, grade, unlogged. Each tool runs in a subprocess with a per-tool timeout (default 20 min, `--timeout`). Status record per tool: `status` in {ok, skipped_no_store, skipped_no_new_input, skipped_up_to_date, failed, timeout}, `seconds`, `exit_code`, output sha256 list, first 300 characters of stderr on failure. The status file also carries the importer's coverage counts (drives with cloud data / drives in master), worded "no cloud data yet" for uncovered drives, never "gap".
Ingestion stage entry: id `cloud_auxiliary`, `verified: false` until it has run in a full ingestion, cmd `python3 tools/cloud_stage.py`.

## 3. Tests (known-answer, `tests/synthetic/`, one CI list line)
(a) no store: exit 0, all `skipped_no_store`; (b) a planted failing tool (exit 1) and a planted timeout: recorded, later tools still run, exit 0; (c) unchanged fingerprints: second run skips as up to date, outputs untouched (sha256); (d) a planted change of `drive_master.csv` between tools aborts the rest and records it; (e) the stage entry in `tools/ingest_stages.json` is before `release_identity`, after the last arrays/payload stage, and the existing ingest-order tests stay green; (f) the status text never uses the word "gap" for uncovered drives (language gate). The six tools keep their existing tests.

## 4. Acceptance and falsification
Accepted when the tests pass, CI is green, a dry run on this machine's real store finishes with exit 0 and a status record per tool, and the measured total time is reported (if it exceeds 25 minutes the Director decides whether the slow tools, grade and unlogged, become opt-in via `XT_CLOUD_SLOW=1`). Falsified if any planted failure stops the wrapper or an unchanged rerun alters an output.

## 5. Not in scope
No new analysis. No release_check dependency. No dashboard binding. No change to any tool's estimator. `verified` stays false until a full ingestion has run the stage; the first real ingestion run is the check (recorded in the CHANGELOG then). The ingestion session that is active in parallel is not touched: the stage entry lands by PR like any other change and the ingestion skill stays unchanged.

## 6. Questions for the Director
(a) Is placement before `release_identity` right, or should the stage run last so a cloud tool can never delay a gate? (b) Should the slow tools be opt-in from the start (about 11 minutes of the total)? (c) Is "exit 0 always" acceptable for the wrapper, given the repo rule that a failing stage stops the run, or may a crash of the wrapper itself (not a tool) stop the run? (d) Is the fingerprint-skip safe for tools that read `raw/` (clock offset, thermal) when raw changes but the store and master do not?

## 7. Rev 2 (overrides sections 1 to 6 where they differ)
Director rulings on Rev 1 (a)-(d) and required changes 1-8 are adopted; owner chose option A: the pinned tools (grade M737, thermal M734, unlogged M739) are rerun on the new master after an ingestion.
7.1 **Placement.** Last stage before `state`, after `release_check`. `release_identity` hashes only the core files, so earlier placement gains nothing. The stage is never read by `release_check`.
7.2 **Re-pin design (option A).** The registered results stay as published (`M737_g0.json`, `M734_thermal_forcing.json`, `M739_unlogged_exposure.json`, registered on master MD5 `d514d6009d6d9a0a168ad4fb09b9bb98`, 717 drives): they are never overwritten. Each pinned tool gets a `--retest` mode (a tool spec Rev 3 for M737, M734 and M739, each pre-registered as an addendum BEFORE the first retest, with its own hash; no threshold, estimand or decision rule changes) that accepts a master whose MD5 differs from the pin, records `masterMd5`, `registeredMd5`, `retest: true`, the drive count, and writes to `analyses/cloud_retests/<tool>_<master md5 first 8>.json` (the published-result filename is untouched). A retest is a labelled re-run on a larger corpus, not a replacement; wording "retest on N drives (master MD5 ...)". The pin check of the registered mode is unchanged (registered mode still refuses a different master).
7.3 **Stop rules that are not pins stay.** Thermal keeps the M726 event E1 stop (any sub-zero hour in the exposure log): in a retest it records `stopped_E1_M726` (status, not failure) and writes nothing; it is not re-pinnable here, only the winter session / owner can change it. Grade and unlogged keep their own gates (support floor, frozen-file hash checks).
7.4 **Atomic outputs (change 1).** The wrapper runs every tool with `--out-dir` set to a scratch directory; only after exit 0 and a non-stopped result does it promote the files to `analyses/` (or `analyses/cloud_retests/`) by atomic rename. A failure, a stop stub or a killed run never overwrites a committed result.
7.5 **Fingerprint (change 3, answer d).** One fingerprint per tool over all actual inputs: tool file sha256, its spec file sha256, store manifest sha256, master MD5, sha256 of the specific `analyses/` inputs it reads (M729 coverage and gaps CSVs, the M717 exposure log), `seasonal_drive_master.csv`, the `summary_arrays.json` seasonalFits sha where read, `XT_RAW_DIR` resolved path plus a content hash of the raw files it reads (not `raw_manifest.json`), `nb`. Skip only if the fingerprint is unchanged AND the recorded output sha256 matches the file on disk; otherwise rerun.
7.6 **Order and dependencies (change 4).** import, coverage, clock_offset, tyre (needs coverage), thermal (needs coverage and gaps), grade, unlogged. A failed or stopped upstream sets `skipped_upstream_failed` downstream.
7.7 **Protection (change 5, answer c).** Before and after each tool the wrapper hashes the master, `summary_*.json`, `cohort_arrays.json`, `raw_manifest.json`, `release_identity.json`, `analyses/M717_frozen_sources/`, `M717_winter_predictions.json`, `M726_extractor_registry.json`. A change is an integrity breach: remaining tools abort, status `integrity_breach`, wrapper exit non-zero (the one case that stops an ingestion). Tool failures, timeouts and missing inputs exit 0. An exception inside the wrapper is caught, written as `wrapper_error` in the status file and surfaced in `STATE.md` (one line), exit 0.
7.8 **Concurrency and Windows (change 6).** Lock file in the store directory (refuses a second concurrent run, status `skipped_locked`). On timeout the whole process tree is killed (`taskkill /T /F` on Windows, process group elsewhere). Thermal's shared `seasonal_fits_cache` is read-only to the stage: the stage sets a private `--cache-dir` copy path or passes a read-only flag, decided in the tool Rev 3 (the seasonal_fits stage must not see a cache write).
7.9 **Raw directory (change 7).** `mynissan_clock_offset.py --raw` defaults to `XT_RAW_DIR` when set.
7.10 **Declared outputs (change 8).** The stage entry lists `analyses/cloud_stage_status.json` and `analyses/cloud_retests/` under `outputs` and names that the stage is optional; the existing "gaps" keys of the coverage tables stay; test (f) concerns the status prose only.
7.11 **Slow tools.** grade and unlogged run only when a new export was imported in this ingestion OR the master MD5 changed since their last recorded run, and `XT_CLOUD_SLOW=1` is not required for correctness (a changed master is the trigger); `--timeout` default 20 min each. Measured total time reported at the dry run.
7.12 **Parallel ingestion.** The `ingest_stages.json` entry and the wrapper land by PR after the running ingestion has merged (a merge conflict in the stage list is likely otherwise); the dry run uses this worktree's own master and a scratch out-dir, never the shared `raw/` in write mode.
7.13 **Order of work.** (i) tool Rev 3 addenda for M737, M734 and M739 (retest mode) with tests, Director review; (ii) wrapper and stage entry with tests; (iii) blind audit of the stage contract; (iv) Director decision; (v) dry run on this machine; (vi) PR. `verified` stays false until a full ingestion has run it.

## 8. Rev 3 (overrides sections 1 to 7 where they differ; adopts the seven required changes of the Director review of Rev 2)
8.1 **No stub in registered mode.** Each pinned tool's Rev 3 addendum changes registered mode so that on a stop (pin mismatch, E1) it writes NOTHING into `analyses/` (the stop record goes to stdout or the scratch out-dir only). Today thermal, grade and unlogged write a stub over the committed `M7xx_*.json` on a stop; that behaviour is removed, with a test.
8.2 **One directory per retest run.** Retest outputs go to `analyses/cloud_retests/<tool>_<master md5 first 8>/` and hold ALL of the tool's outputs (including `M734_park_gaps.csv` and `M734_ambient_drives.csv`). Nothing outside that directory is written in retest mode. `cloud_retests/` is committed with the ingestion (public repository: aggregates and the per-drive-day tables the registered runs already commit; no coordinates, no tracks).
8.3 **Protected set extended.** Section 7.7's set also contains the registered `M737_g0.json`, `M734_thermal_forcing.json`, `M734_park_gaps.csv`, `M734_ambient_drives.csv`, `M739_unlogged_exposure.json` and `seasonal_fits_cache/` (read-only to the stage). A change is an integrity breach.
8.4 **Slow-tool trigger.** A tool reruns when its 7.5 fingerprint changed (this replaces 7.11's trigger). `XT_CLOUD_SLOW=0` is an opt-out recorded as `skipped_opt_out`.
8.5 **Per-tool Rev 3 and the fallback.** Until a tool's Rev 3 addendum is registered (hashed, committed, before its first retest), the stage records `skipped_pinned_master` for it. `docs/open_items.md` (M737 and M739 rows) is rewritten to "retest via the cloud_auxiliary stage; registered results stay".
8.6 **Known-answer test per tool (condition i).** Retest mode on the pinned master `d514d6009d6d9a0a168ad4fb09b9bb98` reproduces the registered numbers byte-identically apart from label fields (`retest`, `registeredMd5`, output path). A retest is descriptive only, never a new verdict. If a retest flips a registered decision or leaves a registered interval, it goes to the Director and nothing is superseded automatically. Repeated retests are repeated looks at the data: no confirmatory wording; every retest JSON carries the label "retest on N drives (master MD5 ...)", never "updated" or "confirmed", and the scope line "M726: not read by the winter session".
8.7 **Use of the outputs.** No payload key, dashboard, article or winter use of `cloud_retests/` without a Director decision and Andrii's sign-off. (The dashboard request of 2026-11-22 is handled in its own milestone, `analyses/M748_spec.md`, which reads only the registered results, not the retests.)
8.8 **Release check staleness.** An integrity breach after `release_check` makes that pass stale; the wrapper records it, exits non-zero and the operator reruns `release_check`.
