## 1. Defect (read from the code and the raw headers; the counts are re-derived by script in the implementation)
`compute_summary_arrays.py:6729-6730` reads only `[BMS] Input possible power (hp)` and `[BMS] Output possible power (hp)` (`_HDRM_PP_IN_COL`, `_HDRM_PP_OUT_COL`) and converts with `_HDRM_HP_TO_KW = 0.745699872` (mechanical horsepower). Header scan of `raw/` (author, read-only, header only, this session): 252 files carry the `(hp)` pair (dates 2026-08-14 to 2026-09-30), 4 files (2026-05-15 to 2026-08-13) carry the `(hp)` pair plus an extra `(Short) (hp)` pair, 176 files (2026-09-30 to 2026-11-09) carry the `(kW)` pair, never both; 244 files carry neither. The payload block `headroomUtilization` covers 253 of 434 scanned files (38.0 %): every `(kW)`-era drive is silently dropped.
Unit: 86.6758781031239 hp (the constant Output value of the `(hp)` era, M140) x 0.73549875 (metric horsepower) = 63.750 kW = 255 x 0.25 kW; with the mechanical factor it is 64.634 kW (1.4 % too high). The `(kW)` files carry values on a 0.25 kW grid with a maximum of 63.75 kW (sample read by the author: Input 26.0 to 63.75; Output values from 55.0 up to 63.75, i.e. Output is no longer a hard constant in the `(kW)` era). So the `(hp)` columns are metric hp converted from the same byte-coded quantity, and a one-byte ceiling (255 x 0.25 kW) is a possible saturation.
Stale statements in the block: `outputCeilingConstant: False`, `outputCeilingRangeKw [60.58, 64.63]`, the methodology string (constant 86.68 hp ceiling, 23 files, about 9 %), the dashboard text at `xtrail_summary.jsx:12907-12930`.

## 2. Changes (pre-registered, no tuning after the result)
Loader `_headroom_utilization_events`: per file choose the `(kW)` pair when present, else the `(hp)` pair converted with `HP_METRIC_TO_KW = 0.73549875` (constant named and sourced: metric horsepower, PS); never both (if a file carries both pairs the `(kW)` pair is used and the two are compared; any difference above 0.05 kW on the aligned samples stops the build). The `(Short)` columns are not read. The era of each file (`hp` or `kW`) is recorded per event.
Unit validation gate (hard stop): in the `(hp)` era the maximum of the Output possible power converted with the metric factor must equal 63.75 kW within 0.01 kW on at least 90 % of the covered `(hp)` files; otherwise the build stops and the Director decides.
Censoring flag (D-04): per era and pooled, the number and share of possible-power samples equal to 63.75 kW (tolerance 0.01 kW after the conversion), for Input and Output separately, and the number of files with at least one such sample; the utilisation statistics are reported for all events and for events whose possible power is below 63.75 kW (the second set avoids a possibly saturated denominator). Wording: 'possibly saturated at 63.75 kW (255 x 0.25 kW); not identified'.
Coverage statement written into the payload by the script: files scanned, files carrying the channel by era (`hp`, `kW`), files analysed (a usable I-V pairing), files without the channel, date range of each era, events per direction per era.
Per-era reporting: chargeUtilization and dischargeUtilization (median, p95, max, nAbove1, maxEvent) pooled AND per era; the alignment tolerance of 2 s (`_HDRM_ALIGN_TOL`) is kept and its stale-match caveat stays; nothing is clipped.
Keys: existing keys keep their names; new keys are additive (`coverage`, `eras`, `ceiling`, `unit`); `outputCeilingConstant` and `outputCeilingRangeKw` are recomputed per era from the data, and the methodology text is generated from the counts (no typed '23 files', '9 %', '86.68 hp').
Ingestion: WITHDRAWN (Rev 1 R3): the block is refreshed at every ingestion by the full arrays build; no new stage.
Dashboard: `xtrail_summary.jsx` text and figures bind to the new keys (coverage, per-era rows, ceiling flag); the old literals are removed and the old wordings added to `language_gate.py` RULES with this ledger id.
