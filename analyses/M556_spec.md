# M556 spec Rev 1 (2026-11-01, before any code): signal-validity registry for the BMS 12 V channel and other sentinels (audit 2026-10-29 N05)

Status: PRE-REGISTERED DRAFT for Director review. Nothing implemented. Tier B (data-validity metadata, no estimator). Branch base: `main` at M555 (`15ff08c`). Ledger id `AUD29-N05`. Acceptance (audit): an all-zero voltage yields "unavailable", never zero physical supply or a battery fault; raw zeros are preserved; no chart or conclusion is invented. Audit figures for the 12 V channel are corroboration only and are not typed into the repo.

## 0. What exists and what the corpus shows (surveyed on disk before this spec)
- The intake-air sentinel (-100 degC) is handled in the master by a [-40, 90] bound (CHANGELOG M319, `tools/data_health.py`, `tools/intake_air_block.py`); nothing reusable exposes it as a declared rule.
- `[BMS] 12V Battery Supply Voltage (V)` is present with samples in some files and every non-missing value in every such file is exactly 0. No analysis in the repository reads the channel (grep over the pipeline and tools finds no consumer), so nothing changes numerically; the gap is that the channel's invalidity is not declared anywhere a future reader could consult.
- Two sparse, location-specific voltage channels exist in other files (an ELM327 adapter supply channel and an ECU supply channel, values of the order of a 12 V system); they are not the BMS 12 V channel and support no battery-ageing, rest-state or DC/DC-efficiency statement.
- A generic "all values zero in a file" rule is NOT a sentinel rule: many app-calculated engine and fuel channels are all zero in drives where the engine never ran (zero is a physical state there), and some turbo-position channels are all zero in many files. A sentinel therefore needs a per-channel declaration with its physical justification; an inventory of all-zero channels may be reported but never auto-classifies a channel as invalid.

## 1. Question and non-question
Which channels have a declared validity rule, and per channel what are the instrument location, the rule, the period and extent over which it holds in the corpus, the sampling freshness, the resolution and the analyses the channel may support? Non-question: no physical interpretation of a zero reading, no 12 V health, ageing or DC/DC statement, no change of any master column, no suppression of raw data (raw zeros stay in `raw/` and in any file-level reader).

## 2. Registry and tool
- Registry file `signal_validity_registry.json` (hand-curated declarations, versioned in the repo): per channel `id`, `column` (exact header string or a documented regex), `instrumentLocation`, `rule` (kind: `all_non_missing_equal` with a value, or `value_equals` with a value, or `declared_sparse`), `physicalJustification` (why the value cannot be a physical reading of that channel), `status` (`unavailable_when_rule_holds`, `sparse_location_specific`, `handled_upstream`), `permissibleAnalyses` and `impermissibleAnalyses` (short lists), `references` (CHANGELOG / spec ids).
- Declared entries: (1) `bms_12v_supply` - rule: every non-missing value in a file equals 0 (a 12 V system supply cannot read 0 V while the logger is powered by it): status unavailable when the rule holds; (2) `intake_air_minus100` - `[BMS] HV Battery Intake Air Temperature (degC)` value -100 is the documented sentinel, status handled_upstream (the master NaNs it by the [-40, 90] bound, M319), the tool only counts it; (3) `elm327_supply` and (4) `ecu_supply` - status sparse_location_specific (descriptive only).
- Tool `tools/signal_validity.py` reads each raw file's declared columns only (usecols), verifies each declaration against the corpus and writes the additive payload block `signalValidity`: per entry the number of files carrying the column, files where the rule holds, days, samples, active period (first and last date), the share of the channel's files where the rule holds, freshness (samples per second of drive, median across files), resolution (the `signal_representation.json` grid step where present, else decimals), and the observed value range; plus an INVENTORY of the channels that are all zero in at least one file (top entries by file count with the file / day / sample counts) labelled "zero can be a physical state; not a validity declaration" unless the channel has a registry entry. No file, master column or analysis is changed.
- Reader contract (`signal_validity.status(column, values)`, pure, unit-tested): given a declared column and a vector of values, returns `unavailable` when the rule holds and the values otherwise; it never returns a number for an unavailable channel and never modifies the input. It is the API future consumers must use for the BMS 12 V channel; the registry check asserts that the declared consumers list is empty today.

## 3. Known answers (pre-registered)
- KA1 an all-zero vector of a declared `all_non_missing_equal` channel -> unavailable; a vector with one non-zero value -> not unavailable (the rule is all-or-nothing per file); an empty vector -> not testable (never unavailable by default).
- KA2 the reader returns the input unchanged object-wise (no mutation, raw zeros preserved).
- KA3 (hard gate, real corpus): for every declared entry, the number of files where the rule holds plus the number where it does not equals the number of files carrying non-missing samples of the column (partition identity, checked against an independent `read_csv` + `notna` count); a miss stops.
- KA4 the BMS 12 V entry: no file carries a non-zero non-missing value of the channel (if one does, the declaration is falsified and the milestone escalates; it is not silently relaxed).
- KA5 no registry entry has an empty required field; every `permissibleAnalyses` list excludes battery-ageing, rest-state SoC and DC/DC-efficiency statements for the sparse supply channels and excludes any physical statement for an unavailable channel (tested).
- Expectations (not gates): the BMS 12 V channel is all zero wherever it has samples (the audit's observation); the inventory contains engine / fuel channels whose zeros are physical. Disagreement is reported.

## 5. Payload, display, language
Additive block `signalValidity` (+ stamp), ingestion stage `signal_validity` (re-verifies the declarations on new files; a new all-zero BMS 12 V file is counted, a non-zero value escalates). Display: a short Methods-tab paragraph with a table of the registry entries (channel, location, status, files and days where the rule holds, active period, permissible analyses) and the sentence that raw zeros are preserved; no 12 V chart. Language (ledger AUD29-N05): "unavailable (all logged values equal 0 in N files)", "declared validity rule", "sparse, location-specific observations"; never "0 V supply", "battery fault", "dead 12 V battery", "failed DC/DC", "12 V ageing", "rest-state SoC from the 12 V channel"; N always script-written.

## 7. Rev 2 (2026-11-01): Director review (verdict revise, minor); incorporated. Rev 1 SHA-256 before this edit: 6f16a55f0f090e54de9f05fed7f29dd6dcf8130090f9ff4b6cdf3393c265537f
Where this section and sections 1-6 differ, this section governs. No re-review unless an A3 trigger fires.
- R1 (population). Counts are over the raw files that map to master rows (606); header-only-empty files (header present, no non-missing value) are counted separately and not credited; the surveyed raw files are reconciled against the master rows, the auxiliary exports and the comparison-only captures as in M555, and a mismatch or an unparseable file other than the known auxiliary export escalates (unparseable files are listed).
- R2 (equality). Values are parsed from the text fields as numbers; "0", "0.0", "-0" all equal 0 exactly; empty, non-numeric and NaN are missing, never zero. The rule is per file: `all_non_missing_equal` holds iff the file has at least one non-missing value and every non-missing value equals the declared value.
- R3 (reader contract). `signal_validity.status(entry_id, values)` returns an object `{status, values}`, never polymorphic: `status` is `rule_holds_unavailable` (values is None: the values are withheld, raw input untouched), `rule_not_holding` (values returned unchanged; for `bms_12v_supply` a mixed file additionally raises an escalation flag and the zeros are never returned as readings), or `not_testable` (empty or all missing; never unavailable by default). Registry schema gains a `consumers` field; a static grep test asserts that no module other than the registry tool references the BMS 12 V column (today the list is empty).
- R4 (inventory). The all-zero inventory uses `signal_representation.json` min / max / n_nonnull where a file is present there (117 recent files) and a full read otherwise; the coverage of each source is stored. The tool therefore reads all columns once per file (cached per raw sha256), which replaces the Rev 1 "declared columns only" statement; the inventory is payload-only and appears in the display as one count line.
- R5 (audit sample). The sample is selected from file headers: every file carrying the BMS 12 V header (stratified by day, up to 14 files), 4 files without it, up to 4 files each carrying the adapter and the ECU supply headers, up to 3 header-only-empty files (if any) and up to 3 files with a -100 intake-air sample; the auditor reproduces column existence, n non-missing, non-zero count, min / max and the rule verdict from the rule text; exact tolerance.
- R6 (registry governance). The registry SHA-256 is stored in the payload and the stamp; the ingestion stage never edits the registry; an entry change needs a spec revision and a CHANGELOG id.
- R7 (resolution). Resolution is null when the channel has fewer than 5 distinct values in the file (all-zero channels) with that reason stated; no decimals fallback is presented as sensor resolution.
- R8 (justification, entries, language). The `bms_12v_supply` justification states only that a powered 12 V system cannot physically be at 0 V and that the cause of the 0 response is unknown. Entries (3) and (4) carry the exact header strings (`Напруга (ELM327) (V)` and `Напруга на ЕБУ (V)`); entry (2) is the exact `[BMS] HV Battery Intake Air Temperature (℃)` header. Language gate rule (AUD29-N05): additionally never "sensor fault", "invalid sensor", "measured 0 V", "not supported by the ECU"; "holds in the corpus", never "always".
- R9 (intake air; Q6). The -100 count is re-derived from raw with the declared column only, status stays `handled_upstream`, values outside [-40, 90] that are not -100 are reported separately, and no master change is made.
- R10 (extra triggers). Escalate also if header-only-empty files exceed 5 % of the channel's files, if a header regex matches more than one column in a file, if a new file at ingestion carries any non-zero BMS 12 V value, or if the intake-air column has out-of-bound values other than -100.
