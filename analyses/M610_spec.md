# M610 spec (Rev 0, written before any code): gate-aware ingestion - one discovery pass per batch, no repeated work after a stop

Status: Rev 0, 2026-11-10. Owner request: Andrii, chat 2026-11-10 ("perform the assessment ... the process should be split into small pieces and failing on the next small piece should not invalidate the whole process already done", then "Yes, spec it").
Prerequisite: M609 (branch `claude/m609-ingest-resume`, commit 634a450): root run logs excluded from the data state, ack/ruling files survive a rollback, resume is the default. This milestone builds on it.
Tooling only. No estimator, gate threshold, gate meaning, acknowledgement requirement, payload key or published figure changes. Nothing here lets a stop pass without the ruling it needs today.

## 1. Evidence (read from `runs/*/status.json` and `failure.json` on 2026-11-10; the cost report in 3.A recomputes every number below by script, nothing here is to be typed into a result)
- 124 recorded runs, 97 `gate_failed`, 27 `ok`. Failing stage counts: release_check 20, ingest_core 13, leaf_guard 13, gtr_family_refresh 12, build_html 9, urban_week_block 5.
- Batch Nov 5-9 (33 drives): six failed full runs of 37, 46, 56, 56, 83 and 137 minutes (about 415 min); the unique stage work up to the furthest stage reached (stage 65 of 87) is about 137 min; about 280 min were repeated.
- Root causes found (analysis of this session): (R1) resume never matched because a run log inside the tree changed the base key (fixed by M609); (R2) `ingest_core` is one 46 min stage with 12 internal `Gate` raise points and no sub-checkpoint; (R3) escalations are discovered one per rerun: four different Director/gate stops appeared in sequence in this batch (estimator switch in ingest_core, sensitivity flip in gtr_family_refresh, M494 verdict stop in urban_week_block, stage-order defect at thermal_provenance); (R4) stage order is not validated: M606 `thermal_provenance` reconciles with `thermalSupportLedger` but ran before the stage that refreshes it.
- The runner stops at the first non-zero return code (`run_ingest.py` stage loop: `rc != 0` -> status, `failure.json`, break, journal rollback). Stops that need a ruling exit with 3 in nine tools (`gtr_family_refresh_splice`, `gtr_closure_refresh`, `urban_week_block`, `urban_balance`, `m338_lhv_splice`, `m471_etabus_splice`, `m473_splice`, `m510_fuel_routemix_splice`, `m511_fuel_eligibility_splice`); the stage JSON does not distinguish an escalation from a failure, and the facts a Director needs live only in each tool's last log lines.

## 2. Design principles
P1. A stop that needs a ruling is information, not an error: record it, keep going on the assumption that the ruling will be "acknowledge", report all of them together. P2. A discovery pass never commits and never changes what a real run would produce. P3. The real run after the rulings must not repeat the discovery pass's work: the stage chain restores it. P4. Every deviation from today's sequential behaviour is covered by an equivalence control on real data (4.E). P5. Hard failures (integrity gates, ML16, pre-existing row diffs, TOCTOU, manifest) are NOT escalations and still stop immediately.

## 3. Components (three deliverables, in this order; each is a separate milestone commit with its own tests)
### A. M610a: stage-order lint and repeat-cost report (low risk, no runtime change)
A1. `ingest_stages.json` gains an optional per-stage `needs: [stage ids]` (blocks it reads that another stage writes; the file-level inference below cannot see payload keys of the shared `summary_arrays.json`). Seed list: `thermal_provenance` needs `thermal_support_ledger`; the other seeds are derived from the audit of the 87 stages in section 5, reviewed, not guessed.
A2. `tests/synthetic/test_stage_order.py`: (i) every `needs` entry exists and precedes its stage; (ii) file-level: for each stage, the repository files named in its code closure (reusing `ingest_checkpoint.closure`) that are declared `outputs` of another stage must be produced by an earlier stage, unless the stage lists a reasoned waiver `reads_prior_state: [file]`. Negative control: the pre-M609 order (thermal_provenance before thermal_support_ledger) must fail (i).
A3. `tools/ingest_cost_report.py`: from `runs/*/status.json` per batch (a batch = consecutive runs with the same master-before MD5 or the same journal base) prints stage executions, minutes executed more than once, unique minutes, and the share of repeated minutes; read-only; output `analyses/ingest_cost_report.json`.
### B. M610b: stop protocol and collect mode
B1. `tools/stop_protocol.py`: `record_stop(stage, gate, kind, facts, ack_env, withheld)` writes `runs/<ts>/stops/<stage>__<gate>.json` = `{stage, gate, kind: "escalation", facts (compact JSON, < 2 KB, values copied from the tool's computed result, never typed), ackEnv, ackSchema, withheld: [payload keys or files not spliced], recordSha256}`. Only `kind: "escalation"` stops are collectable; the nine exit-3 tools above and the two `ingest_core` acknowledgeable gates (`--ack-estimator-change`, `--ack-recalibration`) are converted, each by a minimal wrapper at the existing raise point; the gate condition and its message stay byte-identical.
B2. `run_ingest.py --collect-stops` (alias of env `XT_COLLECT_STOPS=1` for the stage tools): a converted tool that would stop on a ruling-bound gate instead writes its stop record and proceeds as if the ack were present (it performs the splice it would perform after an accepted ack). Every other failure (return code != 0 without a stop record) still stops the pass at once. The pass ends with `result: "collect_done"`, exit code 4, `runs/<ts>/stops.json` (all stop records in stage order, first-stop index, count) and a draft Director brief per stop (facts + ack schema). The journal ALWAYS rolls the tree back at the end of a collect pass, so nothing is committed or left in the tree; `release_check` and the stamp stages run inside the pass so that stops from them are found too.
B3. Chain promotion (P3): checkpoints are saved in a collect pass. A stage executed after a recorded stop gets the chain key `K_i = H(K_{i-1}, id, code hash, stopRecordSha256 of every stop recorded so far)`. The real run, with each ack bound to its stop (ack file carries the `recordSha256` it was issued against, checked by the tool: an ack for a record that differs from the live one is refused as today), computes the same keys and restores the discovery pass's work instead of re-executing it. If a ruling is "not acknowledge", or the facts differ in the real run, the keys differ and the chain re-executes from the first changed stage on (correct by construction, slower).
B4. The Director brief template lists ALL stops of the batch at once with their facts; the existing rule "stage prints ESCALATE -> research-director -> ack" is unchanged; the collect pass only changes when the stops are found, not who decides.
### C. M610c: `ingest_core` candidate cache
C1. First deliverable of C is instrumentation only: per-phase wall-clock inside `ingest_core` written to `runs/<ts>/ingest_core_phases.json` (no behaviour change), because the 46 min are not yet attributed (expected: drive extraction, master append and ML16, arrays recompute, energy MC, determinism check). C2 is specified only after C1 data exist (Rev 1).
C2 (provisional): the expensive candidates (candidate master, candidate arrays before the acknowledgeable gates) are cached under a git-ignored `ingest_core_cache/` keyed by sha256 of the new raw files, `summary_config.json`, the code hash of `ingest_core` and its import closure, and the previous master/arrays blobs; a rerun after an ack-only gate failure re-evaluates the gates on the cached candidates (target: minutes, bytes identical to a fresh run). Cache entries are additive, never read without a full key match, and never used by `--fresh`.

## 4. Pre-registered known-answer tests (written before the tools)
T1 (A2) order lint: finds the thermal_provenance-before-thermal_support_ledger defect on a copy of the pre-fix stage list; passes the current list; a `needs` cycle and a missing id fail.
T2 (B2, toy chain): 3 converted stages each emitting an escalation stop, one hard-failing stage after them. Pass 1 `--collect-stops` finds exactly the 3 stops and stops at the hard failure (not at the first stop); with the hard failure removed ends `collect_done`, tree bytes equal the pre-run bytes, exit 4, `stops.json` has 3 records in stage order, no ack needed. Pass 2 real run with the 3 acks: each stage executes at most once across both passes beyond the restore, result `ok`, final bytes equal a sequential run of the same chain that was acknowledged stop by stop.
T3 (B1) record schema: facts < 2 KB, `recordSha256` stable, a changed fact changes the hash; an ack bound to another hash is refused.
T4 (B3) key promotion: same facts -> restore; changed fact in one stop -> that stage and later re-execute, earlier stages restore.
T5 (C, after Rev 1): cache hit only on a full key match; each key component changed in turn invalidates; bytes equal fresh.
T6 regression: the existing checkpoint, journal and run_ingest tests and `tests/synthetic/test_ingest_resume_robust.py` stay green; with no flag the runner behaves as after M609.

## 5. Equivalence control on real data (blocks merge of B; independent of the author)

## 6. Acceptance (measured by `ingest_cost_report.py`, not asserted)
After M610b, on the next ingestion with at least two stops: no stage executes more than twice per batch (discovery pass + real run), and repeated minutes <= 20 % of unique minutes (this batch: about 67 % repeated: 280 of 415 min, figures to be recomputed by the report). After M610c, an ack-only failure inside `ingest_core` costs less than 10 minutes to re-evaluate.

## 7. Risks and decisions for the Director
D1. Collect mode proceeds "as if acknowledged": downstream stops are computed on the assumption of acceptance. If a ruling is "do not acknowledge", the real run re-executes from that stage (B3 makes this correct, not fast). The brief must say that downstream facts are provisional. D2. Acknowledgement files stay human inputs issued after a ruling; the collect pass never writes one. D3. Which of the 12 `ingest_core` gates are collectable: only the two with an existing `--ack-*` option; all integrity gates stay hard stops. D4. A converted tool's gate condition must not change: the wrapper tests compare the tool's stop/no-stop decision on the stored inputs of M575, M578 and M608 against its decision before conversion.
Not in scope (parked): running independent stages in parallel (the `needs` table in A makes it possible later; sequential execution stays the rule); any change to what a gate checks; the Ukrainian companion article.
