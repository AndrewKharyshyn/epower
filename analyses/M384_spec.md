# M384 spec (Rev 1): regen_seasonal_raw parity guard on a no-new-files rerun (diagnosis + proposed gate change)

Status: Rev 1, Director review pending. Nothing implemented beyond the read-only diagnostic `tools/m384_parity_diag.py` (output `analyses/M384_parity_diag.json`).

## Facts (read from disk, 2026-10-06; master MD5 7c3bc9883f223e8a488b84ad053e13b5)
- `tools/regen_seasonal_raw.py` (M341) refuses to splice a RAW-class seasonal chart unless the all-rows fresh builder result equals the stored top-level block byte-for-byte (canonical JSON, `canon(out["all"]) == canon(top)`).
- On a no-cache run it fails for CrawlStopGo and EngineStartsByType (with the M380 code too). The committed `analyses/M341_check.json` of M376 reports `framesLoaded: "cached"` (0 frames loaded): its parity was produced from cached results.
- Diagnosis (two fresh computations are equal to each other: deterministic): 0 leaves have a different value; the stored blocks carry ADDITIVE leaves that the fresh builders never write: CrawlStopGo 15 (`/phaseEnergy/blindAudit/*`, restored by stage `post_splices` from `analyses/M356_blindaudit_record.json`), EngineStartsByType 44 (per-type `maxDrive, maxKm, median, n, nDays, nShort, p10, p25, p75, p90, shortKm`, added by a post-build splice, M362).
- In a real ingestion `ingest_core` rebuilds the top-level blocks fresh (no additive leaves), so parity holds, `refresh_raw_seasonal` then lists the chart as refreshed, and the splices re-add their leaves afterwards. In a run with no new files `ingest_core` is a no-op, the additive leaves persist, parity fails and the two charts leave `seasonalCharts._staleness.refreshedRawCharts.keys`; `leaf_guard` then stops the run (`UNEXPECTED LOSSES`, 2 leaves).
- No published value is affected: the guard fails closed (nothing spliced from a failing chart).

## Proposal
Parity := every leaf of the fresh all-rows block exists in the stored block with an identical value (stored may carry additional leaves; none may differ or be missing). Record per chart `additiveStoredLeaves` (count) in `M341_check.json`. A changed or missing leaf still fails; conservation checks, cutpoint scan and the splice itself are unchanged. Known-answer tests: identical -> pass; changed value -> fail; stored superset -> pass with the count; fresh has a leaf the stored lacks -> fail.
Rejected alternatives: (a) leave the guard and re-run only after a fresh ingestion (the no-change run, and the M385 skip validation, can never be green); (b) drop additive leaves before comparing by a hand-kept list (a second list to maintain).

## Questions for the Director
1. Is superset-equality an acceptable replacement for byte equality in this guard (no false-optimistic path: a drifted value or a missing leaf still fails)? 2. Should `refreshedRawCharts` stay as is (the chart counts as refreshed when its fresh block is a subset of the stored one)? 3. Is a blind audit required for a tooling-only gate relaxation of this kind?

# Rev 2 (Director ruling "revise, then go"; blind audit PASS; implemented)
Rulings. Superset equality accepted with required restrictions: (1) arrays must have EQUAL length and every element is compared recursively; extra leaves are allowed only as extra dict keys, never extra array elements; (2) extra keys only at path patterns registered by the splice that owns them, READ from the splice definitions (`tools/post_splices.ADDITIVE_LEAVES`, `tools/m362_splice.ADDITIVE_KEYS`; `summarise()` asserts its keys equal `ADDITIVE_KEYS`), not from a list kept in the guard; (3) per chart `M341_check.json` records `parityMode` (exact|superset|notEvaluated), `additiveStoredLeaves` (count and patterns), `framesLoadedAllRows`; parity is NOT evaluated (and fails closed) when no frame was loaded for the all-rows run; the all-rows result is never taken from the result cache; (4) `refreshedRawCharts` keeps its meaning but gains `additiveLeavesNotRefreshed` (leaves owned by the splices are not presented as refreshed by this step); (5) known-answer tests incl. stored array longer, extra key outside the registered patterns; (6) CHANGELOG states the deviation from the M341 byte-equality rule. Blind audit required (tooling gate relaxation): done.
Audit (analytical-auditor, scoped to the comparator, independent cases): 44 cases, 0 verdict mismatches, no false-optimistic path; observed strictness: -0.0 vs 0.0 differs; residual (not exploitable with the current registries): patterns match on text, so a stored key literally named `x[0]` normalises to `x[i]`.
Result on the live corpus (no cache, `analyses/M384_regen_check.json`): CrawlStopGo superset (15 additive leaves, `/phaseEnergy/blindAudit`), EngineStartsByType superset (44 = 4 elements x 11 registered keys), frames loaded 3,668 and 524; 0 changed leaves, 0 fresh-only leaves.
Limits: the relaxed guard does not check that the additive leaves are correct or current (their own splices and gates do). No published value changes.
