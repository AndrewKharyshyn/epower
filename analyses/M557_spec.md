## 1. Question and non-question
For the quantities the analyses rely on, which are raw logged channels, app-calculated channels, derived quantities, constants or model outputs; what is each derived from; and does every check in the evidence ledger and every named negative control validate its target through a source that is independent of it, or is it circular or a shared-input check? Non-question: no change of any estimate, no new physical claim, no automatic discovery of dependencies from code (declarations are hand-curated and reviewed), no re-ruling of any existing validation status in this milestone (conflicts are reported and escalated).

## 2. Registry and tool
- `channel_dependency_graph.json` (hand-curated, versioned): nodes with `id`, `label`, `kind` (`raw_logged`, `app_calculated`, `derived`, `constant`, `model_output`), `source` (header string, code reference or spec id), `parents` (node ids), `derivation` (one line, for example "P = I x V / 1000", "fuel rate and fuel counter are both app-calculated from the same engine-load inputs"). Required families named by the audit: MAP / boost, fuel rate / fuel counter, power / current / voltage, capacity constants (`CAP_KWH`, the rated 5 Ah lead), and target / actual signals (torque, rail pressure).
- `independence_claims.json` (hand-curated): one row per check or negative control with `id`, `target` (node id of the quantity being validated), `validator` (node id or list of node ids of what validates it), `declaredClass` (`independent`, `shared_input_check`, `coding_check_only`, `model_adequacy`, `negative_control`), `nullMechanism` (required for a negative control: why the quantity must be null there), `ledgerRef` (the `evidenceLedger` row and check label, or the payload path).
- Tool `tools/dependency_audit.py` computes, from the graph, for each claim: the ancestor and descendant sets of target and validator, the shared raw ancestors, and a COMPUTED class: `circular` (validator is an ancestor or descendant of the target, or they share the same derivation node), `shared_raw_input` (disjoint derivation but at least one shared raw or app-calculated ancestor), `independent` (no shared ancestor beyond declared constants), `not_applicable` (model adequacy and negative control are checked against their own rule: a negative control must carry a null mechanism and its target must not be a descendant of the quantity it is supposed to be null for). The payload block `channelDependency` stores the graph summary, the claims with declared and computed classes, the mismatches, and the coverage check that every `evidenceLedger` check and every named negative control above has a claim row. Nothing in the payload or the dashboard values changes.

## 3. Known answers (pre-registered)
- KA1 a validator that is a child of the target (target T, validator f(T)) -> circular; a validator that is a parent -> circular; a validator with the same single parent as the target (siblings) -> shared_raw_input; two disjoint chains to distinct raw channels -> independent.
- KA2 a shared constant (`CAP_KWH`) alone does not make two claims dependent only if declared as a constant node; a shared raw channel always does (tested both ways).
- KA3 a negative control without a null mechanism is rejected by the schema check; a negative control whose target is a descendant of the quantity it is supposed to be null for is circular.
- KA4 (hard gate, real registry) coverage: every `evidenceLedger.rows[*].checks[*]` and every listed negative control / falsification clause has exactly one claim row; no orphan claim; a miss stops.
- KA5 the graph is acyclic (topological sort succeeds); a cycle stops.
- KA6 every parent id exists; every non-raw node has at least one parent; every raw / app-calculated node carries a source string that exists as a header in at least one raw file or in `signal_representation.json` / the master header (checked by the tool, not typed).
- Expectations (not gates, reported either way): the "same-algorithm re-implementation" check computes as circular or coding_check_only; the M220 independent re-integration computes as shared_raw_input (same current and voltage channels, different algorithm); the fuel rate / fuel counter pair computes as shared_raw_input or circular depending on the declared derivation.

## 7. Rev 2 (2026-11-01): Director review (verdict revise); incorporated. Rev 1 SHA-256 before this edit: ee46202383bacb587c7520ad4f57f852bbe93096ba8396d82edd7c09a830a3f4
Where this section and sections 1-6 differ, this section governs. Correction of fact: the evidence ledger has 5 rows and 6 checks (not 7); the named controls are found by the deterministic scan of R3 (7 hits), so the registry has 13 claim rows.
- R1 (vocabulary; Q1). Node kinds: `raw_logged`, `app_calculated`, `latent_unlogged` (inputs inside the app or ECU that are not logged, e.g. fuel-rate model inputs, target / actual command inputs), `derived`, `constant`, `model_output`, `external_reference` (ambient, ODO, OEM specification; none is needed by the claims declared now). A shared app-calculated or latent ancestor counts as a shared input. Every `app_calculated` node and every ECU / VCM target-or-actual node carries a declared parent (possibly a latent node); a node of these kinds with no parent fails the schema and can never compute as independent. A validator set that contains the target is circular. "Same derivation" is the explicit node field `sameDerivationAs` (a declared id), not inferred from text.
- R2 (classes and axes; Q1, Q2). Computed classes: `coding_check_only` (the validator is declared `sameDerivationAs` the target or vice versa); `circular` (the validator or the target is an ancestor of the other, or the validator set contains the target), EXCEPT that a model_output descendant of a model_output target (same model, different split or order) is `model_adequacy`; `shared_raw_input` (disjoint derivation but at least one shared raw_logged, app_calculated, latent_unlogged or external_reference ancestor); `independent_conditional_on_unverified_constant` (no shared data ancestor but a shared `verified:false` constant, whose agreement says nothing about that constant); `independent` (no shared ancestor at all). Each claim also records three DECLARED descriptive axes (channel overlap, sample overlap, algorithm), which are not computed. Pre-registered expected classes before any run: E1 coding_check_only, E2 shared_raw_input, E3 circular, E4 model_adequacy, E5 model_adequacy, E6 shared_raw_input; the controls C1-C7 compute as negative_control when their requirements pass (below).
- R3 (coverage and controls; Q3). Coverage is checked against (a) every `evidenceLedger.rows[*].checks[*]` and (b) a deterministic scan of the payload keys with the pattern stored in the claims file (negative controls, misspecification controls, falsification clauses, S0 control and any key ending in "Control"), with every exclusion listed with its justification in the claims file; a scan hit without a claim, a claim without a hit, or an excluded key without a justification stops the stage. Each control claim carries `expectedOutcome` (null, nonnull, nonnull_one_sided, bias_reference or decision_rule), a `nullMechanism` and the OBSERVED outcome read from the payload at run time (never typed). `lowSpeedDissipation...negativeControl` is a bias-reference control, not a null control.
- R4 (audit design; Q4). The graph and claims hashes are frozen and recorded in the CHANGELOG before the audit; the auditor receives neutral labels (any self-declared "independent" wording is stripped), the class definitions of R2 and read access to the repository code and the payload, but not the graph, the claims, the declared classes or the tool; they return for each claim the raw ancestors of the target and of the validator and a class. The comparison is on the raw-ancestor sets as well as the class; every disagreement is listed; only the Director settles it; no silent post-audit edit of the graph.
- R5 (conflicts; Q5). A conflict between a computed class and a ledger row's wording is REPORTED with a marker beside the row in the payload and the display; no `validationStatus` or displayed status is lowered in this milestone (a separate Director ruling). Extra triggers: the computed class is weaker than an `independent` label wording; a negative control moved against its expectedOutcome or has no recorded outcome; a claim shares a `verified:false` constant; an app_calculated node has no declared parent; an existing dashboard string would fail the new language rule; the ledger row for gross throughput carries evidence class "measured" on a derived quantity and the coastKw note says "measured" (reported, not changed here).
- R6 (reconciliation; KA6). Node ids are reconciled with `signalValidity` (M556) entries and with `tools/stamp_dependencies.json` (M513) where they name the same producer; the code or payload references of the derived and model nodes must resolve (an existing payload key, file or function, checked by the tool). Raw_logged and app_calculated nodes carry an exact header string that must exist in at least one raw file.
- R7 (stage and language). The ingestion stage stops if a computed class changes between runs. The language rule (ledger AUD29-N08) is scoped to the NEW strings of this milestone; the existing hits ("Independent re-integration", "independently corroborated") are listed in the CHANGELOG entry for the Director and left unchanged. Display: a table with the current validationStatus, the conflict marker, and the graph hash and date, plus a note that the declarations are hand-curated.
