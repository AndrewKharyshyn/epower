Not yet assessed (do before the build): whether the 1-3 decimal values (22,776 leaves) carry unjustified precision (e.g. 3 decimals on a quantity whose CI is +-0.1); a sample audit by quantity class is part of the control, not a claim of this spec.

## 2. Proposed rules (per quantity class, one display formatter layer)
R1 Counts (drives, days, events, trips, transitions) are integers; thousands separator by the existing formatter.
R2 An estimate with a CI is shown with the decimals set by the CI half-width: the number of decimals is chosen so the half-width has 2 significant figures at most, never more decimals than the stored value; point and both limits use the same decimals. Fallback when no CI: 3 significant figures.
R3 p-values only through `fmtP` (no raw p digits in text); effect-size ratios 3 significant figures.
R4 Energy sums (kWh, drive/session level): 2 decimals; GTC (kWh-equivalent) 2 decimals; km 1 decimal; minutes 1 decimal (existing); SoC pp 1 decimal (existing).
R5 Rates below 0.01 (fuel per km and similar): 3 significant figures, no fixed decimals.
R6 Voltages: 3 decimals (1 mV logger resolution); currents 1 decimal; temperatures 0-1 decimal as now.
R7 Anything that is a quoted payload constant keeps its stored text where a methodology note must state it exactly (CAP_KWH, thresholds); listed explicitly, not inferred.
R8 Exports (JSON/CSV downloads, tooltips that state "exact value") keep full precision; only the on-screen text changes.
