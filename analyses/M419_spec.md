# M419 spec (Rev 1): artifact-stamp schema split - when a block was computed and on what basis versus when it was included in the release (audit F06)

Status: pre-registration, written before the tool. Metadata only: no payload number, no estimator and no dashboard figure changes. Branch `claude/next-milestone` from `main` (f5134f6, M418). Origin: deep audit 2026-10-11 F06 / self-audit p8 ("historical stamps conflict"), FEASIBILITY.md row F06 ("split computedAt/inputBasis from includedInReleaseAt; carried blocks keep their historical basis; fully doable"), owner direction 2026-10-12 ("go as you recommend").

## Facts on disk (to be reproduced by the tool and the gate, not typed)
- `_artifactStamps` has 155 keys. `corpusHash` is the live master MD5 on all of them (build_html.js aborts otherwise, M220.2) and `generatedAt` is the time of the STAMPING PASS (the `socHysteresisV2` note already says so). Neither field says when a block was computed or on how many drives.
- `masterRefitAudit`: the block holds the 446-row clean-room audit of 2026-09-25 (published master `0bcfc400...`), but its stamp says `computationStatus: computed`, `carriedForward: true`, `basisNDrives: 489` and a note "carried forward at the 489-drive basis". Status, flag, basis and note contradict each other and the block (446 is in the block; the 489-row rebuild is `masterRefitProvenance`).
- `masterRefitProvenance`: stamp `computed` with `carriedForward: true`, `basisNDrives: 489`; the block is historical (rebuild from the former re-exports, before M366).
- `seasonalCharts` and `generatorTractionRecon` keep `carriedFromMaster: true` and an M293 `carryForwardNote` (446 / 410 drives) beside current notes that say the blocks were regenerated on 554 drives (`seasonalCharts._staleness.stillStale == []`; only `crossval` is stale in `generatorTractionRecon.staleBlocks`). Nothing in the code reads these two keys (one comment in `tools/m332_w1a_splice.py`).
- `socHysteresisV2` is the only stamp with `computationStatus: carriedForward`; its block states `nDrivesCovered: 489` (`currentCorpusSize: 554`, `frozenBasis`) and has no timestamp.

## Schema (additive on every stamp; nothing is renamed)
- `includedInReleaseAt` = the stamp's `generatedAt` (the stamping pass). `generatedAt` stays for compatibility and the gate requires equality.
- `computedAt`: for a block with its own timestamp, that value read from the block (`masterRefitAudit.generatedAt`); for a computed block without one, the stamp's `generatedAt` (the block was computed or regenerated by the stamping pass of this release); where the block has no timestamp and is carried (`masterRefitProvenance`, `socHysteresisV2`), `null` with `computedAtNote`.
- `inputBasis` = `{nDrives, masterMd5, source}` read from the block's OWN fields where it declares them (table `BLOCK_BASIS` in the tool: `masterRefitAudit` -> `nRowsPublished` / `publishedMasterMD5`; `masterRefitProvenance` -> `rebuildFromRepositoryArchive.nRowsRebuilt` / `.publishedMasterMD5`; `socHysteresisV2` -> `nDrivesCovered`; `seasonalCharts` -> `_staleness`; `generatorTractionRecon` -> `staleBlocks.perBlock`), otherwise the stamp's `corpusHash` and `meta.totalDrives` with `source: "stamping pass"`. The tool never types a number.
- Carried blocks: `computationStatus` = `carriedForward`, `basisNDrives` = `inputBasis.nDrives`, and the note is regenerated from these fields (`masterRefitAudit`: "clean-room audit of N rows, published master M, generated D; not re-run on the live corpus; the 489-row rebuild is masterRefitProvenance"). The M293 `carriedFromMaster` / `carryForwardNote` pair is replaced by a derived `carriedBlocks` list (from `_staleness.stillStale` and `staleBlocks.blocks`) and the old text is kept as `supersededCarryNote` (history, not a current statement).

## Wiring
`tools/stamp_basis.py` (modelled on `tools/stamp_notes.py`: idempotent, allow-list guarded to `/_artifactStamps/*`, `--dry-run`), run by `tools/restamp_ingest.py` (the existing ingestion stage) after `restamp_blocks` and `stamp_notes`, so no new stage entry is needed; `tools/restamp_blocks.py` now sets `computationStatus` together with `carriedForward` (the root cause of the contradiction); leaf-guard rules for the intentionally corrected leaves (scoped to M419, condition `field_changed` on the named keys). The stamping pass of a rebuilt arrays object recreates the stamps; the stage regenerates the new fields (derived, so idempotent).

## Gates (semantic_gate + known-answer test, in CI)
1. Every stamp has `includedInReleaseAt == generatedAt`, `computedAt` null or <= it, and an integer `inputBasis.nDrives`.
2. `computationStatus == computed` -> no `carriedForward` / `basisNDrives`; `carriedForward*` -> `basisNDrives == inputBasis.nDrives == the block's own declared count`; the note contains that count.
3. `masterRefitAudit`: status carriedForward, basis 446 = `nRowsPublished`, master MD5 = `publishedMasterMD5`; `masterRefitProvenance`: basis 489.
4. No stamp carries `carriedFromMaster` while the block's own staleness record lists nothing carried at that basis.
5. Mutation tests: a hand-edited basis, a flag on a computed stamp, a note with a different count, a missing field each fail.

## Acceptance and limits
Tool + tests + gate green; `release_check.py` and CI green; payload numbers byte-identical outside `/_artifactStamps` (diff proves it); CHANGELOG `M419`. Limits: `computedAt` of a block without its own timestamp is the stamping pass or null (the information does not exist in the repo and is not reconstructed from git history); the stamps are not rendered on the dashboard, so there is no dashboard figure change.
