# Workflow and tools (imported from Claude memory `workflow-and-tools`, last updated 2026-09-22)

Ground truth for state is `python tools/state.py`. Statements here predate M299; where they conflict with disk/CHANGELOG, disk wins.

## Ingestion protocol (each batch)
1. Archive the 16 ML/domain columns -> `analyze_bytes` x N (new files) -> append/sort -> `postprocess_master` -> restore ML16 byte-exact (0/16 diffs required).
2. `build_summary_arrays` with `frame_loader` + `raw_loader` + `prev_arrays` carry-forward + `recompute_energy_mc=True` + `recompute_m119v2=False`.
3. `crosscheck_vehicles.inject()` + `crosscheck_events.inject()` (both MD5-assert `drive_master.csv` unchanged).
4. `corpus_manifest.build()` via the clean `raw_only/` directory workaround.
5. `determinism_check.py` regeneration written to BOTH `summary_config.json.auditMetadata.determinism` AND `summary_arrays.json.determinism` (prevents silent reversion).
6. `build_html.js` -> `validate_jsdom.js` (9/9 tabs, 0 console errors).
7. T-01..T-04 + T-01b acceptance tests.
8. Seasonal data recomputed on EVERY ingestion: `compute_seasonal.py` (`seasonal_drive_master.csv`/`seasonal_arrays.json`/`cohort_arrays.json`), refresh
   `summary_arrays.json.seasonalCharts._meta.cohortCounts` and `generatorTractionRecon`/`seasonalCharts.charts.GeneratorTractionRecon` (`refresh_gtr_headline.py`, after any
   `fuel_recon.py --all`), re-run `speed_split.py` + `battery_temp_extremes.py` (its row-count-match gate silently drops 2 `records` rows if its CSV lags the live corpus).
   `seasonalCharts.charts` has ~50 entries, all with confirmed generators (`category_A(dm)`/`category_B(dm, raw_loader)` cover 30; 16 more are `_xxx(dm, ...)` raw-pass
   functions; `_crawl_stop_go` and `_thermal_fuel_penalty` cost ~150-260 s/cohort and need pickle-checkpointed part1/part2 calls in a time-limited sandbox - not needed on a normal machine).
   Always verify each function's "all"-cohort output byte-exact against its non-cohort top-level `S.*` counterpart (JSON-round-trip both sides first) before trusting a Warm/Shoulder split;
   where no such anchor exists, an exact eligible-row-count match against the pre-refresh basis is the fallback standard.
- Andrii's standing instruction: seasonal data and the `seasonalCharts`-dependent side-scripts (`wire_gtr_seasonal.py`, `refresh_gtr_headline.py`, `battery_temp_extremes.py`, `speed_split.py`) are recomputed on every ingestion.

## M119-v2 pack-temperature ladder: refit procedure and drift monitor (M320 / M321)
- The surfaces use a data-derived, support-gated ladder (`socHysteresisV2.tempLadder`, `tools/m320_ladder.py`, spec `analyses/M320_spec.md`). It is tied to the V2 fit basis and carried between refits.
- Every ingestion runs the report-only drift monitor (stage `m321_ladder_monitor`, `tools/m321_ladder_monitor.py update`, spec `analyses/M321_spec.md`): it extends the exact per-drive histogram cache `analyses/M321_tpack_cache.json` for NEW files only and writes `socHysteresisV2.tempLadderMonitor`. Status `ok`, `warn-refit` (W1 distribution shift, W4 support loss) or `warn-newspec` (W2 cold candidate on a non-overlapping band, W3 range extension >= 1 grid step). A `warn-newspec` needs an acknowledgement record in `analyses/M321_acknowledgements.json` (`{warningSetHash, ref, date, selectionCodeSha256, basisNDrives}`, written by hand after the decision; `ref` must name an existing CHANGELOG `## M###` heading or an existing `analyses/` spec file, and the record must carry the current basis identity so an old-basis acknowledgement cannot clear a recurring warning set) or `release_check.py` FAILS; it never triggers a silent refit.
- After an explicit `recompute_m119v2` refit the gate FAILS until the ladder is re-derived: `python tools/m318_run.py tables --n-first <N> --out TABLES.pkl`, `python tools/m320_ladder.py run --tables TABLES.pkl --out DIR`, `python tools/m320_ladder.py apply --out DIR`, `python tools/m321_ladder_monitor.py rebase --tables TABLES.pkl`, `python tools/m321_ladder_monitor.py update`. Editing `m119v2_model.py`, `tools/m318_run.py` or `tools/m320_ladder.py` also invalidates the cache (selection-code hash, whole files, CRLF-normalised): re-run `rebase` (about 10 min); comment-only edits of those files force it too, by design (a false invalidation is cheap, a stale cache would silently corrupt the monitor).
- Evidence for the monitor: `python tools/m321_validate.py` (writes `analyses/M321_result.json`), tests `tests/synthetic/test_m321_monitor.py`. On Windows run with `PYTHONUTF8=1`; write `summary_arrays.json` with LF endings.
- When the monitor reports `warn-newspec` (cold-season W2/W3 is likely): copy `analyses/TEMPLATE_ladder_warning_spec.md` to `analyses/M###_spec.md` and fill it BEFORE any result (Director review, blind audit); after the decision write the acknowledgement with `python tools/m321_acknowledge.py --ref "M### <title>" --note "..."` (refuses unless the status is `warn-newspec` and the ref resolves; never run from ingestion).

- **fit_glm fallback (F14, M431).** `m119v2_model.fit_glm` silently refits with tol 1e-6 and `scale=1.0` on ANY exception of the primary fit (which can drop the clustered covariance and accept a singular design without a record). Census of the published fit sequence (`tools/fit_glm_census.py`, evidence `analyses/F14_fit_glm_census.json` and `analyses/F14_m320_draw_census.json`): 549 fits, 0 fallbacks, 0 non-converged, 0 rank-deficient, 0 warnings, so no published number came from that path; no downstream code reads `bse` / `cov_params`, so the clustered covariance is never consumed. The module is NOT edited standalone (the selection-code hash would invalidate the M321 cache and the existing W2/W3 acknowledgements). **Refit checklist (do these together with the next explicit `recompute_m119v2` refit):** (1) replay the refit's fits with `python tools/fit_glm_census.py --tables TABLES.pkl --out analyses/F14_fit_glm_census_<M###>.json` and require 0 fallback / 0 non-converged / 0 rank-deficient (and `--mode m320` for the ladder draws); (2) in `m119v2_model.fit_glm` replace the silent fallback by `tools/fit_contract.fit_glm_strict`'s contract (raise instead of falling back) and write the per-fit record into the block; (3) re-key the monitor (`rebase`, `update`) and re-issue the W2/W3 acknowledgements under the new hash. New code that fits this estimator uses `tools/fit_contract.fit_glm_strict` (same numbers when the contract holds; raises `FitContractError` otherwise); tests `tests/synthetic/test_fit_contract.py` pin the current silent behaviour so any change to it is deliberate.

## Input-plausibility gate and signal-representation record (M308 / M324 GateA2)
- `tools/plausibility_gate.py` runs on every NEW raw file before ingestion (fail closed, flag-only, never repairs, never applied to the published master). R1 = cell-voltage range (pooled); R2 = quantisation, tested PER CHANNEL on the Max and Min cell-voltage columns (one flag lists the channels that trip). A channel with < 5 distinct values or no numeric values is `untested`; `ingest_core_report.json` lists such files under `plausibility_partial` (visibility, not a quarantine). Spec: `analyses/M308_plausibility_gate_spec.md`, `analyses/M324_gatea2_spec.md`; tests `tests/synthetic/test_plausibility_gate.py`.
- Residual false negatives: a partly coarse channel (statistic = minimum positive step) and a channel with < 5 distinct values still pass.
- `tools/signal_representation.py` writes one record per NEW file to `signal_representation.json` (hashes, header fingerprint, cadence, per-channel grid/decimals/range). It is written LAST by `ingest_core` (after the master write; a failed earlier step leaves no entry), is additive and byte-identical on re-run, fails closed on a sha256 conflict (legitimate re-export: `python tools/signal_representation.py FILE --supersede KEY`). Descriptive only: say "grid of this CSV copy", never "sensor resolution". No pipeline or build step reads it yet. Tests `tests/synthetic/test_signal_representation.py`.

## Journaled release (M416, audit F20)
`tools/run_ingest.py` snapshots the working tree (everything except `raw/`, `raw_only/`, `raw_cache/`, `runs/`, `audit/`, `.git`, `node_modules`, caches; files above 30 MB are hashed, not copied) into `runs/<ts>/journal/` before the first stage.
A failed stage, an exception or SIGINT/SIGTERM restores every changed file, removes created files, re-creates deleted files and re-hashes the tree (`rolled_back`, or `rollback_failed` with the mismatches, exit 4). A green run is committed: `journal.json` keeps the write set (changed / created / deleted) and the undeclared writes, the snapshot copies are deleted.
A killed runner leaves the journal `started` and `runs/.release.lock`: the next run refuses to start (exit 5) until `python tools/run_ingest.py --recover`. Flags: `--keep-on-failure` (inspect the mixed state; journal stays open), `--no-journal` (development only).
Not covered: `raw/` is never modified by a rollback (raw files added by a failed run are listed in `status.json` under `journal.rawAdded`); there is still no single-pointer release directory (blocked by the flat-tree rule in MIGRATION.md): readers can see the mixed state during a run, the lock file and the journal mark that window.

## Gate stops and reruns (M609)
An ingestion takes hours; a failed gate must cost only the stage that failed and the stages after it, never the whole run. Rules that make that work:
- A plain `python tools/run_ingest.py` after a failed run RESUMES: the stages that passed are restored from `runs/.checkpoints/` (chain keys = data state + XT_* env + code hash of each stage). `--fresh` forces every stage. A code fix, a stage reorder, or a new ack / ruling file only re-executes from the affected stage on.
- Do not put run output inside the repo tree under another name than `*.log` / `*.out` at the repo root (those two are excluded from the data state and from the journal snapshot). Preferred: no redirect at all (the run already writes `runs/<ts>/`), or redirect outside the repo.
- Acks and rulings (`analyses/*_ack*.json`, `*_ruling*.json`, `*_director_ruling*.json`, `leaf_guard_rules.json`, `M321_acknowledgements.json`) are human inputs: a rollback or `--recover` never deletes them, and editing one does not invalidate earlier checkpoints.
- Any other data file that changes between a failed run and its rerun (a hand edit of `summary_config.json`, a new untracked data file, a changed raw listing, a changed XT_* variable other than XT_RAW_DIR / XT_ACK_*) invalidates the whole chain on purpose. Make such edits BEFORE the first run of a batch, not between runs.
- Order matters inside the stage list: a stage that reconciles with another stage's block must run after that stage (M606 `thermal_provenance` ran before `thermal_support_ledger` and stopped the Nov 2026 ingestion at stage 65).

## Pre-run checks, stage order and the repeat-cost report (M610a)
- Stage `static_preflight` (first stage, read-only, always re-run): every new raw CSV has a canonical `ambientByDrive` entry, `vehicle.odometerAsOf` equals the newest new drive date, `summary_config.json` and `xtrail_summary.jsx` pass the language gate, the XT_ACK_* files exist and cite an existing ruling, the stage list and `needs` are consistent. Run it alone with `python tools/ingest_static_preflight.py`; it lists what cannot be decided before the run (STAMP_POLICY coverage, REQUIRED_BLOCKS, leaf_guard diff, build_html, semantic_gate B-D).
- A stage that reads a block another stage refreshes declares `needs: [stage ids]` in `tools/ingest_stages.json`; `python tools/stage_order.py` (and CI `tests/synthetic/test_stage_order.py`) fails if a `needs` entry comes later. File-level findings are a ratchet against `analyses/M610_stage_needs.json` (status unreviewed until the Director table, spec E3); a deliberate read of carried pre-refresh state is waived per stage with `reads_prior_state`.
- `python tools/ingest_cost_report.py` (read-only, writes `analyses/ingest_cost_report.json`): per batch executed vs unique minutes, per stop the class (escalation / hard / environment), the cause line, and for every rerun that could not resume the recorded `missReason` (which data file, raw listing or XT_* variable differed from the stored chain). Run it after every batch; the repeated share is the process KPI.
- `ingest_core` writes its phase wall-clock to `runs/ingest_core_<ts>/phases.json` and `tools/ingest_core_report.json` (`phases`), so a later split or cache of that stage is designed from measurements.

## Discovery pass for ruling-bound stops (M610b, opt-in)

`python tools/run_ingest.py --collect-stops` runs the whole chain once so that every stop that needs a Director ruling is found in one pass instead of one per rerun. Only gates that already have a ruling-bound acknowledgement are collectable (`analyses/M610_gate_table.json`: the GTR flip and simultaneity-band stops, the GTR closure escalations, the urban week-block verdict, the urban balance verdict); every other failure, integrity gates, `leaf_guard`, `release_check` and the `ingest_core` acknowledgement gates stay hard stops that end the pass.
In a pass the converted tools write `runs/<ts>/stops/<seq>__<stage>__<gate>.json` (facts under 2 KB copied from the tool's result, `ackEnv`, `ackSchema`, `withheld`, the hashes of the earlier records, `recordSha256`), withhold their splice where the output bytes would depend on the ack content, and exit 0. The runner saves no checkpoints, always rolls the tree back (the journal is never committed), writes `stops.json`, one draft brief per stop under `briefs/` and the artifacts the auditor needs under `provisional/` (labelled never published), and exits with code 6 (`collect_done`; 4 already means a failed rollback).
Collect mode is a runner-issued token file `runs/<ts>/collect.token`, not an `XT_*` variable, so it cannot change the checkpoint key and a stale variable cannot switch a later run into it; `release_check.py` fails while a token file exists. Rulings are issued in stage order; a `do not acknowledge` on one record voids every later record. The pass never acknowledges anything: after the rulings the real run starts as before and repeats the work (chain promotion, which would let it reuse the pass, is a separate milestone M610d and is not built).
